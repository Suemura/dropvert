# ワークフロー・オーケストレーション

## Issue 起点のタスク開始（/start-issue）

- GitHub Issue に紐づくタスクは `/start-issue <Issue番号>` で開始する。Issue の把握 → worktree・ブランチ作成 → planner → 実装 → 検証 → reviewer → PR 作成 → PR レビュー・指摘対応まで、本ルールのフロー全体を 1 コマンドで自走する。作業は Issue 専用の git worktree（`.claude/worktrees/` 配下）で行われるため、複数 Issue の並列作業が可能。
- 詳細手順は `.claude/commands/start-issue.md` を single source of truth とし、本ルール側には手順を重複記述しない。

## 実装計画の策定

- **Plan Mode で計画済みの場合**: planner の起動をスキップし、合意済みの計画に基づいて実装を開始する。
- **Plan Mode を経ずに直接実装する場合**: 些細ではないタスク（3 ステップ以上、または設計上の決定を含む）では **planner エージェントを起動**して実装計画を策定する。
- planner は Sprint Contract（完了条件）を含む計画を返す。この契約がタスクの完了基準となる。
- 状況がおかしくなった場合は直ちに手を止めて planner を再起動し、無理に進めないこと。
- 次のいずれかに触れる変更は、規模が小さくても「些細ではない」として扱い planner を通す:
  - 元ファイルをゴミ箱へ移動する経路（`trash.js` の呼び出し元、成功判定、`LIST` の生成）
  - 並列実行の仕組み（`xargs -P`、`inputs/NNN` と `results/NNN` の対応、`noclobber` による出力名の予約）
  - stdout の契約（`convert.sh` の 1 行契約、`run.sh` のサマリ契約、作業ディレクトリの契約）
  - `build.sh` の署名まわり、`Info.plist`、bundle の内容

## Subagent 戦略

- メインのコンテキストウィンドウをクリーンに保つため、subagent を惜しみなく活用する。
- 以下は**必ず subagent に委譲する**:
  - **実装計画**: planner エージェント（上記参照。Plan Mode で計画済みならスキップ）
  - **完了前レビュー**: reviewer エージェント（下記「完了前の検証」参照）
  - **リサーチ・調査**: Explore タイプの subagent
- **サブエージェントには差分とコンテキストを手渡す**: 起動プロンプトに差分（`git diff origin/main...HEAD --stat` 等）・変更概要（何を・なぜ、2〜3 文）・関連ファイルパス・実行済みの検証結果を埋め込み、エージェントがコードベースをゼロから探索し直さないようにする。このリポジトリは 5 ファイルしかないため、対象の層（`Dropvert.applescript` / `run.sh` / `convert.sh` / `trash.js` / `build.sh`）を名指しで伝えるだけで探索はほぼ不要になる。
- 複雑な問題には、subagent を介してコンピュートリソースを投入し、1 つの subagent につき 1 つのタスクとする。
- **ビルドと実ファイルの変換テストは subagent に任せず、メインエージェントが実行する**。`./build.sh` は `~/Applications/Dropvert.app` を作り直し、変換テストは元ファイルをゴミ箱へ移動しうるため、結果の確認まで責任を持てる側で行う。reviewer は構文チェックのみ実行し、ビルド・変換の結果はメインエージェントの報告を根拠に判定する。

## 完了前の検証

- 動作を証明しないまま、タスクを完了にしてはならない。**このリポジトリには自動テストも CI も無い。実行して確かめる以外に正しさを示す手段がない。**
- 「これを見た人間（または Staff engineer）は承認するか？」と自問し、実際にコマンドを実行し、出力を確認し、正確性を示す。
- 最低限の静的チェック（変更した層に応じて）:

```sh
osacompile -o /dev/null Dropvert.applescript   # AppleScript を変更した場合
bash -n convert.sh && bash -n run.sh           # シェルを変更した場合
./build.sh && codesign --verify --deep --strict ~/Applications/Dropvert.app
```

- あわせて CLAUDE.md「テスト方法」の該当ケースを実行する。テスト素材は必ず `/tmp` 配下に作り、ユーザーの実ファイルを使わない（変換に成功するとゴミ箱へ移動されるため）。
- 実行できなかった検証項目は、勝手に「確認済み」と書かず、報告・PR 本文に明記する。
- 独立レビューは **reviewer エージェント**が担う。PR を作るタスクでは PR 作成前に 1 回（`/start-issue` の手順 9）、PR を作らないタスクでは完了報告の前に起動する。reviewer が不合格を返した場合は修正して検証をやり直し、合格するまで完了としない。
- 変更ログは専用ドキュメントに書かない（記録先はコミットメッセージと PR 説明）。

## ドキュメント同期

専用の docs-sync エージェントは持たない。以下に該当する変更のときだけ、メインエージェントが `README.md` / `CLAUDE.md` を更新する。該当しなければ何もしない。

- 利用者から見た挙動の変更（対応形式・品質・通知文言・進捗表示・ゴミ箱の扱い）
- ビルド手順・引数・出力先の変更
- stdout の契約・作業ディレクトリの契約の変更
- ファイル構成・責務分担の変更、新しい外部コマンドへの依存
- 新たに踏んだ macOS 固有の落とし穴（CLAUDE.md「注意点」に追記する）

CLAUDE.md には変更ログや実装詳細の羅列を書かない。増やすのは「次に同じ地雷を踏まないための知識」だけに限る。

## PR 作成後のレビューフロー

このリポジトリには PR 検知フックが無いため、**自分で起動する**。

1. `/review-pr <PR番号>` — PR をレビューし、インラインコメントを投稿する
2. `/resolve-pr-comments <PR番号>` — コメントに対応（修正・返信）し、push する
3. 対応結果のサマリーをユーザーに報告する

subagent に委譲する場合は、起動プロンプトに Issue / タスクの要約・変更ファイル一覧・実装意図を埋め込む（探索削減）。

## エレガントさの要求（バランスよく）

- 些細ではない変更を行う際は一時停止し、「もっとエレガントな方法はないか？」と自問する。
- 場当たり的 (hacky) だと感じた場合は、今知っている知識を活かしてより良いソリューションを実装する。ただし過剰なオーバーエンジニアリングは避ける。
- **ただしこのプロジェクトでは「機能を足さない」が第一の選択肢である**。設定 UI・オプション・常駐要素を増やす案は、シンプルさという機能を削っている。エレガントさの追求が機能追加に向かったら、まず「足さずに済ませる案」を検討する。
- 逆に、CLAUDE.md「注意点」に列挙された遠回りな実装（`NSFileManager` によるゴミ箱移動、`noclobber` による予約、`ps -o command=` による生存確認、バックグラウンド起動 + ポーリング）は、素直な実装が macOS 上で壊れた結果として選ばれている。「もっと簡単に書ける」と感じても、理由が注意点に書かれていないか先に確認する。

## 自律的なバグ修正

- バグレポートを受け取った場合は詳細な指示を単に待つのではなく、ログやエラーから自律的に特定し修正を試みる。
- 再現手段を先に作る。`convert.sh` / `run.sh` は単体で直接呼べるため、まず最小の再現コマンドを `/tmp` の素材で組み立てる。ドロップ操作込みの再現は `open -a ~/Applications/Dropvert.app <files>` で行う。
- ユーザーへのコンテキストスイッチ（作業の中断と指示出しの負担）を極力減らすこと。
- ただし、**元ファイルの喪失に関わる報告（変換していないのに消えた、失敗したのに消えた等）は、原因の切り分けより先にユーザーへ状況を伝える**。ゴミ箱から復元できるうちに知らせる必要がある。
