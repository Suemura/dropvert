GitHub Pull Request のコードレビューを行ってください。

PR: $ARGUMENTS

## 手順

※ 呼び出しプロンプトに変更概要（タスクの要約・変更ファイル一覧・実装意図）が含まれる場合はそれを起点にし、レビューは diff 範囲とその直接の参照元 / 参照先に集中する。diff 範囲外のコードベース探索はしない。

1. `gh pr view $ARGUMENTS` で PR の概要を確認
2. `gh pr diff $ARGUMENTS` で diff を取得し、変更内容を把握
3. 以下の観点でレビューを実施
4. 問題がある場合、インラインコメントとして PR に投稿

## レビュー観点

CLAUDE.md の「設計上の原則」「注意点」が最優先の判断基準。以下は diff に該当する項目だけを見る。

### 設計上の原則（違反は原則 [重要]）

- **シンプルさが機能である** — 設定 UI・常時表示のウィンドウ・環境設定ファイル・ドロップ以外の操作が増えていないか。進行度表示が AppleScript 標準の `progress` プロパティ以外の手段になっていないか
- **元ファイルの削除は必ず検証の後** — 出力の存在とサイズ 0 でないことの確認を経ずにゴミ箱へ移動していないか。`rm` を使っていないか（`trash.js` の `trashItemAtURL` 以外で消していないか）。失敗したファイルが削除経路に混入しうるか
- **既存ファイルを上書きしない** — 出力名の衝突時に `-1`, `-2` … の採番が働くか

### 責務分離と stdout 契約

- `convert.sh` の 1 行契約（絶対パス / `SKIP` / `FAIL:理由`）を守っているか
- `run.sh` のサマリ契約（`TMP` / `CONVERTED` / `SKIPPED` / `UNPROCESSED` / `LIST` / `FAIL`）と作業ディレクトリの契約（`results/` / `cancel` / `exit`）を守っているか
- 契約を変更している場合、依存する側（`run.sh` と `Dropvert.applescript`）も同時に直っているか
- `convert.sh` / `run.sh` に元ファイル削除が混入していないか。`Dropvert.applescript` に変換ロジックが混入していないか

### 並列実行の安全性

- 複数プロセスの stdout を 1 つのパイプに集約していないか（入力と結果の対応が崩れ、失敗ファイルの削除事故になる）
- 出力名の採番が `noclobber` による予約のままか（`while [ -e "$out" ]` に戻していないか）。EXIT trap が予約より前に設定されているか
- `inputs/NNN` と `results/NNN` の 1:1 対応が維持されているか

### macOS 固有の落とし穴

- ビルド後に bundle の中身を書き換えた場合、`codesign --force --sign -` による再署名まで行っているか
- ゴミ箱への移動に Finder の AppleEvent を使っていないか
- `do shell script` の引数に `quoted form of` を通しているか
- droplet の PATH に無い外部コマンドを増やしていないか（`shellPrefix` の更新が要る）
- パスをコマンドラインに積み上げていないか（一時ファイル / NUL 区切り + `xargs -0 -n 200` を維持しているか）
- ゴミ箱へ移動するコマンドにパイプを足していないか（`do shell script` は末尾コマンドの終了ステータスしか見ない）
- `run.sh` の生存確認に `kill -0` を使っていないか（PID 再利用で無限ループ）。待ちループに時間の上限があるか
- `display notification` の成否で処理結果を判断していないか

### 一般

- バグ・潜在的な不具合、エッジケース（スペース / 日本語 / 絵文字 / 改行を含むファイル名、`.JPG` など大文字拡張子、フォルダのドロップ、壊れたファイル）
- シェルスクリプトの引用漏れ・未クォート展開・`set -e` 前提の崩れなどインジェクション相当の問題
- 形式非依存の方針を壊していないか（WebP 固有の記述が品質設定と `case` 分岐の外に漏れていないか）
- CLAUDE.md / README.md の記述と実装の乖離

## インラインコメントの投稿

レビュー指摘がある場合、以下の形式で GitHub API を使ってインラインコメントを投稿してください:

```bash
cat > /tmp/review_comments.json << 'EOF'
{
  "commit_id": "{最新のコミットSHA}",
  "event": "COMMENT",
  "body": "このレビューは Claude Code (AI) によるものです。\n\nサマリーをここに記載",
  "comments": [
    {
      "path": "対象ファイルパス",
      "line": 行番号,
      "body": "指摘内容"
    }
  ]
}
EOF

cat /tmp/review_comments.json | gh api repos/{OWNER}/{REPO}/pulls/{PR_NUMBER}/reviews --input -
```

JSON は必ずリポジトリ外の一時ファイル（`/tmp`）に書き出すこと。作業ツリー内に置くと untracked ファイルとして残留する。

## レビュー本文のヘッダー

レビューの `body`（サマリー）の冒頭には必ず以下の一文を入れてください:

> このレビューは **Claude Code (AI)** によるものです。

## コメントのフォーマット

各指摘には以下のプレフィックスを使い分けてください:

- **[重要]** 修正必須の問題（元ファイルを失う危険、設計上の原則の違反、バグ、署名・権限が壊れる変更）
- **[改善]** 強く推奨する改善（可読性、保守性）
- **[軽微]** 軽微な改善提案（命名、フォーマット等）
- **[質問]** 意図の確認や質問

## 出力

最後にレビュー結果のサマリーを表示してください:

- 指摘数（重要 / 改善 / 軽微 / 質問）
- 全体的な所感
